## 二、核心算法：怎么做到无悬崖压缩

### 2.1 理解抽屉

传统压缩的问题像「等房间堆满 200 本书再一次性归档」——中间什么都找不到，归档后什么都找不到。

抽屉的做法像「每 3 本书就放进一个抽屉，抽屉满就把三本书的内容抄到一张便签纸上，贴到下一层抽屉的背面」：

```
抽屉1 (原始对话)
  [msg1] [msg2] [msg3]          ← 满了！
     │       │       │
     └───┬───┘       │
         │           │
     [摘要A] ─────────┤         ← 3条压缩成1条，交到下一层
                     │
抽屉2 (摘要)          │
  [摘要A] [摘要B] [摘要C]       ← 满了！
     │       │       │
     └───┬───┘       │
         │           │
     [元摘要X] ───────┤        ← 再压缩，再交到下一层
                     │
抽屉3 (元摘要)
  [元摘要X] [元摘要Y]           ← 未满，就这两条

每次 LLM 调用时看到的上下文：
  [抽屉1: msg3] + [抽屉2: 摘要C] + [抽屉3: 元摘要Y]
  = 3 条，约 1,700 tok
```

**关键洞察**：抽屉的数量（层数）会随着对话增长而增长，但**每次 LLM 调用看到的条目数永远 ≈ 抽屉数 + 当前层未满数**。不出现「一次性压缩 200 条」的操作。

### 2.2 理解温度 = 命中次数

温度系统的设计来源于一个观察：**在上下文中，时间本身不是问题，被提及的次数才是。**

```
传统方案: 温度 = f(时间, 频率)
  问题: 昨天的重要决策不如今天的寒喧「热」

本方案: 温度 = 命中次数 + 重要性加分
  温度每轮自然衰减(×0.98)
  每次被提到就升温(+1 + 加分)
  重要内容加分更多
```

打个比方：
- 寒喧「好的」= 0 分，相当于给火堆扔了一粒沙子
- 纠正「不对，这个方案不行」= +4 分，相当于加了一块大木头
- 未完成任务「TFC-155 还没做完」= +5 分，相当于浇了汽油
- 情绪爆发「去死」= ∞ 分，相当于直接建了个防火墙

**结果**：重要的东西越来越热，不重要的东西自然冷却。不需要根据时间「猜」什么重要。

### 2.3 理解保护 > 去重 > 更新

这个公式解决的是"三个互相矛盾的诉求"：

```
保护: "这条信息永远不能丢"
去重: "同样的内容不要出现两次"
更新: "有新版本了，旧的可以替换"

问题: 保护要求保留旧版本，去重要求删除重复，更新要求替换旧版本。
      三个要求同时存在时，听谁的？
```

解法：把三个问题**正交化**。

```
保护 = 生命周期问题（删不删）
去重 = 身份问题（是不是同一个东西）
更新 = 版本问题（替换还是追加）

用 key 身份制解耦:
  - 每个实体有一个唯一 key（如 plan:抽屉级联引擎）
  - 保护 = key 对应的条目不参与压缩
  - 去重 = 同 key 不重复推入
  - 更新 = 同 key 的内容可替换（plan）或追加（progress）
```

**就像身份证号**：同一身份证号的人（key）换了新照片（内容）。系统知道这是同一个人，保留最新的照片，但不会删掉这个人的档案。

## 三、代码阅读地图

### 3.1 文件角色

```
__init__.py                 ← 指挥中心
  RoundCompressor             把各组件串起来的「总调度」
  compress()                  核心入口：收到消息 → 过管线 → 输出上下文

drawer_engine.py             ← 海关 + 仓库
  NoiseFilter                 海关：废话走左边通道
  ProtectionDetector          海关：重要文件走绿色通道
  UniqueKeyIndex              海关：同一个人不能排两次队
  ConflictResolver            海关：有冲突找主管
  DedupEngine                 分拣员：重复包裹丢一边
  DrawerStack                 仓库：三个抽屉的柜子
  TemperatureIndex            温度计：哪个箱子最近被打开过

memory_butler/__init__.py    ← 档案室
  MemoryButler                档案员：每 5 轮整理一次文件
  progressive_summarize()     写摘要：有旧摘要就增量更新
  extract_execution_log()     归档执行记录
  archive_completed_task()    冷储已完成任务

context_assembler.py          ← 前台
  assemble_context()          前台小姐：每次 LLM 调用前，把需要的资料准备好
  _vec_search()               去资料库翻文件
  _get_embedding()            查索引卡
```

### 3.2 数据流

```
用户说: "把 TFC-155 的抽屉容量改成 4"

Step 1 | 过海关 (push() 前)
       NoiseFilter: "不是废话" → 放行
       ProtectionDetector: "TFC-155" → 标记 PROTECTED (tfc_ref)
       UniqueKeyIndex: check("tfc_ref:TFC-155") → 新key, pass

Step 2 | 进仓库 (push())
       DrawerStack.push({content: "...TFC-155...", _protected: true})
       TemperatureIndex.hit("TFC-155", importance=1)
         → TFC-155 的热度 +1

Step 3 | 看看满没满
       当前层已 3 条 → DrawerStack.is_top_full = true
       DrawerStack.pop_top() → 取出 3 条
       保护条目(msg with _protected) → 单独放回
       非保护条目(2条) → call_aux_model → 摘要
       摘要推到下一层

Step 4 | 档案室 (每 N 轮)
       MemoryButler.tick()
       → 检测到 TFC-155 → 写入 PG 渐进摘要
       → 扫描执行日志 → 无

Step 5 | 前台准备
       assemble_context()
       → 取抽屉内容: [msg3] + [摘要B] + [元摘要X]
       → 取 L1 热点: TFC-155, 抽屉级联引擎 等
       → 向量搜索: "TFC-155 抽屉容量" → 找到相关历史
       → 输出: < 13K tok 的精炼上下文
```

## 四、设计决策记录

### 为什么不用时间衰减？

**因为在大模型上下文中，时间不是问题。** 昨天做的关键决策和 5 分钟前的寒喧「好的」——对模型来说，时间差带来的影响远小于内容重要性。用「命中次数」替代「时间×频率」更直接。

### 为什么 N=3？

不是精确算出来的，是经验值。N=2 压缩太频繁（每 2 条对话就摘要一次，成本高），N=4 单层太多（4 条原始对话可能已达 20K tok）。3 是个平衡点。

我们把它开放为配置项（`drawer.capacity: 2-10`），你可以改成 4 或 5。

### 为什么不用 LLM 做噪音过滤？

**零幻觉优先。** 如果用 LLM 判断「这句话是不是废话」，你可能得到「基于上下文，我认为这不是废话」——但你没法保证一致性。正则模式匹配 100% 可预测。

而且，LLM 过滤的成本远高于正则：一次 LLM 调用 ≈ 10 万次正则匹配。

### 为什么保护条目要放回头部而不是跳过？

保护条目放回头部（`push_to_head()`）而不是跳过，是因为**保护条目需要保持在上下文中**。如果跳过，保护条目被取走了就没了。放回头部保证它一直出现在 `get_context_items()` 的返回中。

但放回头部也有代价：它占用了当前层的一个位置。如果保护条目太多（比如用户在疯狂纠正），当前层可能永远满不了——因为保护条目一直占着位置。这就是为什么保护条目有数量上限（每层最多 20 条保护）。

### 为什么 light 阶段零 token？

light 阶段（context fill < 20%）调用 LLM 做压缩是浪费——总共才 20% 的窗口，压完能省多少？不如只做机械去重和归档，把省下来的 token 留给真正的压缩阶段。

这个决策的代价是：light→medium 过渡时，第一次 medium 没有前次摘要，需要从头生成。这是一个刻意的权衡——light 阶段省的钱远多于 medium 阶段多花的那一点点。

## 六、常见误解

### ❌ "抽屉 = FIFO 队列"

**不是。** 抽屉栈是 LIFO（后进先出）。新的消息进当前层（最顶层），满了才压缩。`get_context_items()` 从当前层开始取，所以**最近的消息最完整**，越旧的消息摘要程度越高。

### ❌ "温度 = 热度得分"

**不完全是。** 温度是频率 + 重要性，不是纯粹的「热度」。同一个 key 被提到 8 次（+8）和提到 1 次但加了 +7 的重要性加分，效果一样。这是故意的——让一次性但重要的内容（如用户纠正）也能快速升温。

### ❌ "保护 = 永远不被压缩"

**不完全对。** 保护条目不会被抽屉压缩，但会被 context-assembler 的 token 预算限制截断（如果太长会被截到 400 字符）。保护的是「存在性」不是「完整性」——保证上下文里有这个条目，但不保证全文都在。

### ❌ "离线也能跑"

**不能。** 所有辅助模型调用（GLM-4-Flash / Qwen3-8B）依赖外部 API。纯离线模式下 `call_aux_model()` 会返回 None，降级为关键词提取。

## 七、如果你想修改这个系统

### 场景 1: 想要不同的去重策略

改 `drawer_engine.py` 的 `DedupEngine` 类。`dedup()` 方法接收消息列表，返回去重后的列表。你可以增加规则（如按时间窗口去重）、删除规则（如不想用语义去重）、修改规则逻辑。

### 场景 2: 想要不同的保护信号

改 `drawer_engine.py` 的 `PROTECT_SIGNAL_PATTERNS` 字典。增加或删除正则模式即可。不需要动代码逻辑。

### 场景 3: 想要不同的温度层级

改 `drawer_engine.py` 的 `TEMPERATURE_LAYERS` 和 `DECAY_RATES`。调整阈值、token 预算、衰减率即可。

### 场景 4: 想要换一个摘要模型

改 `drawer_engine.py` 的 `AUX_MODEL_CHAIN`。三链：主 → 降级 → 保底。每个链有独立的 `url`、`model`、`api_key_env`、`timeout`。

### 场景 5: 不想用 PG，想用其他数据库

改 `context_assembler.py` 的 `_pg_exec()` 和 `_vec_search()`。两个函数有清晰的输入输出接口，替换为 MongoDB / Redis / SQLite 的实现即可。
