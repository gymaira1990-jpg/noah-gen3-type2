## 一、痛点：大语言模型上下文管理的三大悖论

### 1.1 长上下文的「悬崖失忆」

主流大模型支持 128K–1M token 上下文窗口。但超过 50% 填充率时，几乎所有上下文引擎都会触发「全量压缩」：

```
200K 对话 ──→ [压缩触发] ──→ 20K 摘要

             断崖式降幅, 丢失 90%
```

结果：用户看到「刚才还在讨论的方案，压缩后模型不记得了」。

### 1.2 压缩模型的「灯下黑」

压缩本身需要 LLM 调用——用付费模型做压缩等于「花推理的钱干整理的活」：

| 消耗项 | 比例 |
|--------|:----:|
| 主力对话 token | 100% (必要的) |
| 压缩 token | 30-50% 额外 |
| 其中付费模型 | 100% (冤枉钱) |

### 1.3 每轮压缩的 Boilerplate 浪费

传统压缩模板每轮输出固定格式文本：

- 阶段声明: `[轮数压缩 - light阶段]` 约60tok
- 空摘要段: 6段「无」约30tok
- 指针块: `[已归档可检索]` 约50tok
- 每轮合计浪费 **150-300 token**

## 二、设计哲学

> **核心洞察：200K 上下文的失忆不是压缩不够好，是压缩太暴力。**

### 2.1 抽屉原理

受 office 文件柜启发：不是等到桌面堆满 200 份文件才一次性归档，而是每 3 份文件就放入一个抽屉，抽屉满则压缩成一份摘要递到下一层。

```
抽屉1: [msg1][msg2][msg3] → 摘要A
                                    ↓
                             抽屉2: [摘要A][摘要B][摘要C] → 元摘要X
                                                                   ↓
                                                            抽屉3: [元摘要X]...
```

**效果**：无论对话进行多少轮，上下文永远只有「当前层未满条目 + 每层最新摘要」，通常在 **5 条以内**。

### 2.2 温度 = 命中次数

不是时间衰减（那会让昨天的重要决策遗忘），是命中次数 + 重要性加分：

```
热度层级:
  🔥 L1 (≥8次) → 全量注入上下文
  🌤 L2 (≥4次) → 摘要注入
  ❄ L3 (≥2次) → 搜索可返回
  🧊 Archive    → 知识库归档, 搜索命中才召回
```

重要性加分（代码锁死，非 LLM 判断）：

| 信号 | 加分 | 逻辑 |
|:-----|:----:|:-----|
| 未完成任务 | +5 | 遗忘最痛 |
| 用户纠正 | +4 | 避免重复犯错 |
| 决策记录 | +3 | 方向性选择 |
| 情绪波动 | +3 | 用户在意的事 |
| 路径/API变更 | +2 | 环境依赖 |
| 工具结果 | +1 | 中性记录 |
| 寒喧/确认 | 0 | 无价值 |

### 2.3 免费模型干杂活

| 任务 | 模型推荐 | 成本 |
|:-----|:---------|:----:|
| 主力对话 | 主模型 | ¥（仅推理） |
| 抽屉摘要 | GLM-4-Flash (智谱) | 🆓 免费 |
| 降级摘要 | Qwen3-8B (硅基流动) | 🆓 免费 |
| 机械预压 | LLMLingua (本地) | 🆓 0 token |
| 噪音过滤 | 纯正则 | 🆓 0 token |
| 保护识别 | 纯正则 | 🆓 0 token |
| 上下文组装 | 规则引擎 | 🆓 0 token |

## 三、系统架构：三层级级联管线

```
用户输入 ──→ 每轮对话
                 │
                 ▼
    ╔══════════════════════════════════════════╗
    ║  Layer 0: 预清理引擎                     ║
    ║  机械规则 · 保护标记 · 容量监控          ║
    ╚══════════════════════════════════════════╝
    🅰 通道: 消息级机械规则清理
    🅱 通道: pre_llm_call 保护注入
    🅲 通道: 记忆容量自动归档
                 │
                 ▼
    ╔══════════════════════════════════════════╗
    ║  Tier 1: 抽屉级联引擎                    ║
    ║  6大组件                                  ║
    ╚══════════════════════════════════════════╝
    1. NoiseFilter         ─ 寒喧/确认/元命令 → 不计轮数
    2. ProtectionDetector  ─ 7类信号 → 自动保护
    3. UniqueKeyIndex      ─ key身份管理 → 防重复推入
    4. ConflictResolver    ─ 保护vs去重vs更新 → 裁决
    5. DedupEngine         ─ 精确+语义去重 → 8条规则
    6. DrawerStack         ─ 抽屉级联(N=3) → 满则压
                 │
                 ▼
    ╔══════════════════════════════════════════╗
    ║  Tier 2: 记忆管家                        ║
    ║  5大职责 · 辅助模型异步处理               ║
    ╚══════════════════════════════════════════╝
    ├─ 渐进摘要: 已有方案→增量更新, 不重新摘要
    ├─ 项目追踪: 提取任务引用 → 更新项目档案
    ├─ 日志保护: 识别操作→固化为PROTECTED
    ├─ 冷储归档: 完成任务→最终摘要→向量库
    └─ 重复检测: 当前方案vs历史→防重复造轮子
                 │ (每次 LLM 调用前)
                 ▼
    ╔══════════════════════════════════════════╗
    ║  Tier 3: 上下文组装器                    ║
    ║  5组件融合 · 目标 < 13K tok/次           ║
    ╚══════════════════════════════════════════╝
    组装公式:
      [目标声明] + [Tier1 抽屉摘要] + [L1/L2 热点]
      + [项目摘要] + [向量搜索结果] + [执行日志]
                 │
                 ▼
    大模型(主模型) — 只做推理，不做记忆
```

## 四、组件详解

### 4.1 NoiseFilter — 噪音过滤器

纯正则，零 LLM 调用。检测三种类型：

| 类型 | 示例 | 处理 |
|:-----|:-----|:-----|
| chitchat | "好", "嗯", "ok", "继续", "哈哈" | 不计轮数, 不升温 |
| command | "/compress", "/status", "/help" | 不计轮数 |
| separator | "---", "====", "..." | 不计轮数 |

命中噪音的消息不进入抽屉、不触发温度命中、不计入有效轮数。

### 4.2 ProtectionDetector — 保护识别器

7 类信号自动检测（纯正则，零 LLM）：

| 类型 | 关键词 | 保护级别 |
|:-----|:-------|:--------:|
| plan | "设计:""方案:""架构:""计划:" | ✅ 保护, 版本可替换 |
| correction | "不对""不是的""错了""纠正" | ✅ 永久保护, 全保留 |
| decision | "决定""确认""同意""批准" | ✅ 保护, 同key不重复 |
| emotion | "去死""永久离线""最后机会" | ✅ 紧急全轮保护 |
| progress | "当前""完成""进度""下一步" | ✅ 保护, 追加 |
| execution | "执行了""改了""部署了" | ⚠ session内保护 |
| task_ref | "TASK-001" "PRJ-002" | ✅ 保护, 关键引用 |

### 4.3 UniqueKeyIndex — Key 身份管理

解决「保护 vs 去重 vs 更新」三个正交问题：

```
问题拆解:
  保护 = 生命周期问题（删不删）
  去重 = 身份问题（是不是同一个）
  更新 = 版本问题（内容替不替换）

核心原则: 版本认可最新的
```

| 实体类型 | 唯一 Key | 更新策略 | 去重规则 |
|:---------|:---------|:---------|:---------|
| 项目方案 | `plan:<项目名>` | 原地替换(旧→新) | 同一 key 不重复 |
| 任务进度 | `progress:<编号>` | 追加(每时间戳一条) | 同 key+同日不重复 |
| 执行日志 | `exec:<hash>` | 追加(每个操作一条) | 同会话+同命令不重复 |
| 用户纠正 | `correction:<内容hash>` | 不更新, 全部保留 | 同 hash 不重复 |
| 决策记录 | `decision:<内容hash>` | 不更新, 全部保留 | 同 hash 不重复 |
| 已完成任务 | `completed:<编号>` | 一次性写入, 不更新 | 同 key 不重复 |
| 普通对话 | 无 | 抽屉压缩流转 | DedupEngine |

### 4.4 DedupEngine — 每轮去重

8 条规则，独立于压缩运行：

1. **精确内容去重** — 相同 content 保留最新的
2. **工具结果折叠** — 同工具+同参数, 保留最新
3. **文件读取缓存** — 同一文件路径跳过重复读
4. **终端输出压缩** — 同命令输出保留最新
5. **文件写入冲突** — 同一文件路径保留最后写入
6. **保护条目跳过** — 被保护的条目不参与去重
7. **语义近似检测** — 调用辅助模型判断语义相似（可选）
8. **空内容清理** — content 为空的工具消息删除

### 4.5 DrawerStack — 抽屉级联

核心创新：用小抽屉（容量 N=3）替代「一次性全量压缩」。

```
运行示例（100 轮对话后）:

抽屉1: [msg98][msg99][msg100]    ← 当前层, 未满, 全量保留
抽屉2: [摘要D(轮40-42)] [摘要E(轮43-45)] [摘要F(轮46-48)]
抽屉3: [元摘要B(轮19-36)] [元摘要C(轮37-48)]
抽屉4: [超摘要A(轮1-18)]

上下文 = 抽屉1(3条) + 抽屉2最新(1条) + 抽屉3(2条) + 抽屉4(1条) = 7条
总 token ≈ 1700（而不是原始 100 轮的 200K+）
```

### 4.6 MemoryButler — 记忆管家

每 N 轮触发一次，后台用辅助模型处理：

**渐进摘要**（不是重新摘要）：

```
有旧摘要 → 增量更新: "以下已有摘要[旧], 新增讨论[新], 
                      请增量更新, 不删已有, 只添加新信息"
无旧摘要 → 新建: "提取以下对话中的方案/计划/决策, 
                  输出结构化摘要"
```

结构化格式：

```
## 方案: <名称>
  上次更新: <时间>
  当前进度: <状态>
  已决策: <列表>
  待定: <列表>
  已完成: <列表>
  关联任务: <编号>
  风险/注意: <列表>
```

**执行日志保护**：识别「改了什么」「写了什么」「部署了什么」等操作 → 写入知识库，标记 PROTECTED。

**冷储归档**：完成任务自动向量化 → 最终摘要 300-500 tok → 写入知识库。不占活跃上下文，搜索可命中。

### 4.7 ContextAssembler — 上下文组装器

每次 LLM 调用前执行，目标 **< 13K tok/次**。

```
组装公式（token 预算）:

  [目标声明]            ~200 tok
  [Tier1 抽屉摘要]      ~2000 tok
  [L1 热点 ≥8次]       ~1600 tok
  [L2 热点 ≥4次]       ~1000 tok
  [项目摘要(向量搜索)]  ~1000 tok
  [相关历史(向量搜索)]  ~500 tok
  [执行日志]            ~500 tok
  [用户消息]            ~2000 tok
  ─────────────────────────
  总计                  < 13K tok

不注入:
  - 已完成任务全文
  - 归档方案
  - 寒喧历史
  - 无关项目资料
```

向量搜索降级链：`pgvector ANN` → `全文搜索 ILIKE` → 空结果（静默降级）。

## 五、工程特性

### 5.1 模型切换检测

当用户切换模型导致 context window 变化时，自动限制压缩阶段上限：

```
context_length 缩小 > 30%:
  ├─ 缩小到 1/4 以下 → cap at medium
  ├─ 其他缩小 → cap at light
  └─ 首次正常 → 恢复自主判定
```

### 5.2 预压缩阈值隔离

preflight 检查和 compress() 使用独立阈值：

```
preflight 阈值 = max(常规阈值, context_length × 0.70)
compress 阈值 = context_length × 0.15

原因：preflight 管「切换小窗口会不会撑爆」
      compress 管「对话进行中的 token 优化」
      两件事分开算，互不干扰
```

### 5.3 防抖保护

连续 2 次压缩节省率 < 10% 时自动跳过压缩，防止无效压缩浪费 token。

### 5.4 自进化质量追踪

最近 50 次压缩历史 → 每 5 次调优一次阈值（0.08~0.50 浮动）：

| 触发条件 | 动作 |
|:---------|:-----|
| 自检警告 ≥ 2 | threshold += 0.03（保守） |
| 平均节省 > 30% | threshold -= 0.01（积极） |
| 平均节省 < 8% | threshold += 0.02（放松） |
| 用户纠正 | 记录纠正次数, 影响下轮调优 |

### 5.5 灵魂规则保护

SOUL 级保护标记保证核心规则永不丢失：

- 压缩前: 保护消息不下抽屉、不被压缩
- 压缩后: 验证保护条目是否全在输出中
- 丢失时: 自动重新注入，日志告警

### 5.6 大工具结果文件系统卸载

工具调用结果 > 30K tok 时：

1. 写入磁盘 session 目录下的 offload 子目录
2. 替换为 `[FS Offloaded — tool=xxx size=NNNKB] + 5行预览`
3. 原子写入 `(.tmp → rename)` 防崩溃

### 5.7 消费链恢复

跨会话时读取关键记录（纠正/决策/任务引用/指令），自动注入到新会话的上下文前端。

### 5.8 性能指标暴露

| 模块 | 指标 |
|:-----|:-----|
| MemoryButler | cycles_run, avg_duration_ms, pg_writes_ok/fail, glm_calls/errors |
| ContextAssembler | calls, avg_duration_ms, vec_searches/fail, avg_tokens, sections_avg |

## 六、效果数据

### 6.1 压缩比

| 对话轮数 | 原始 token | 压缩后 token | 压缩比 |
|:--------:|:----------:|:------------:|:------:|
| 0-2轮 | ~20K | 20K (不压缩) | 1:1 |
| 3-10轮 | ~50K | ~15K | 3.3:1 |
| 11-20轮 | ~100K | ~13K | 7.7:1 |
| 21-50轮 | ~200K | ~13K | 15.4:1 |
| 100轮+ | ~500K | ~13K | 38.5:1 |

核心优势：**没有悬崖**。无论多少轮对话，上下文稳定在 ~13K tok。

### 6.2 Token 节省

| 维度 | 传统方案 | 抽屉级联 | 节省 |
|:-----|:--------:|:---------:|:----:|
| 每轮上下文中位数 | 85K tok | 13K tok | **85%** |
| 压缩付费模型调用 | 100% | 0% (全免费) | **100%** |
| 寒喧/确认占上下文 | 5-10% | 0% (过滤) | **100%** |
| 压缩 boilerplate | 150-300 tok/轮 | ~20 tok/轮 | **90%** |
| 决策/纠正丢失率 | ~30% | <1% (保护) | **97%** |

### 6.3 失忆恢复

- 执行日志: 100% 保护（持久化 + PROTECTED 标记）
- 关键决策: 100% 保护（永久保留）
- 用户纠正: 100% 保护（同 hash 不重复, 全保留）
- 已完成任务: 向量冷储, 搜索命中 100% 可回溯
- 普通对话: 渐进摘要, 事实级保真
