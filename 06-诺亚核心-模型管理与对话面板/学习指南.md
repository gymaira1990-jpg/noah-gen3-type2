## 一、阅读路线

按这个顺序读代码：

```
第一遍 — 理解核心数据模型
  kernel.py              ← 先看 ModelConfig / Config，这是所有功能的起点
  models.py              ← 模型 CRUD，3 个函数看懂

第二遍 — 理解 CLI 和 Web
  cli.py                 ← 11 个命令，每个就是一个功能入口
  server.py              ← Web 路由注册，看 5 行就够

第三遍 — 理解自动化
  health.py              ← 健康检查逻辑
  dashboard.py           ← 仪表盘数据组装
  discovery.py           ← 模型发现/搜索

第四遍 — 深入 DeepSeek 适配
  deepseek/params.py     ← 先看 DeepSeekChatParams 和 build_body()
  deepseek/parser.py     ← 再看响应解析
  deepseek/client.py     ← 最后看客户端

第五遍 — 业务理解
  handlers/              ← 看完 API 端点就知道系统能做什么
  deepseek/router.py     ← DeepSeek 特有路由
```

## 二、核心设计决策

### 2.1 为什么不用 Pydantic？

**决策**: 用 Python `dataclass` 代替 `pydantic.BaseModel`。

**理由**:
- 省一个依赖
- 零学习成本——任何 Python 开发者都认识 dataclass
- 功能够用——验证在业务层做，不需要框架级校验

**代价**: 没有自动类型校验，但 100 行的 kernel.py 不需要。

### 2.2 为什么不用 Docker？

**决策**: 纯 pip install，零容器化。

**理由**:
- 4 个依赖不需要 Docker
- Docker 的部署复杂性对于这个项目来说是本末倒置
- 要的是"pip install 即跑"，不是"docker compose up"

### 2.3 为什么特化 DeepSeek 而不是通用？

**决策**: 深度适配 DeepSeek → 做特化而非通用。

**理由**:
- DeepSeek 的 thinking/reasoning 参数是闭源 API 中独特的
- OpenAI 兼容 API 是起点，特化是终点
- 「能做所有事但都做得一般」不如「一件事做得特别好」

但实际上代码是完全 OpenAI 兼容的——你可以添加任何 OpenAI 兼容端点的模型，只是 DeepSeek 的特化功能（思考模式/FIM/Anthropic）不会在其他提供商上生效。

### 2.4 为什么 CLI 和 Web 路由分开？

**决策**: CLI 直接调用 `kernel.py`，Web 通过 FastAPI 路由间接调用。

**这样做的原因**: CLI 没有 HTTP 开销，启动即用。Web 路由叠加了 HTTP 层但提供了图形界面。两者共享 core 模块的核心函数——`load_config()` / `add_model()` / `check_model_health()` 等。

### 2.5 为什么用 YAML 而不是 SQLite？

**决策**: YAML 文件存储配置。

**理由**:
- 人类可读可编辑
- git 友好——配置变更可追踪
- 零依赖——不需要 SQLite3 或 PostgreSQL
- 本项目配置数量极少（通常 3-10 个模型），YAML 足够

## 三、模块依赖图谱

```
kernel.py
├── models.py     → 依赖 kernel 的 Config/ModelConfig/save_config
├── health.py     → 依赖 ModelConfig
├── chat.py       → 依赖 ModelConfig, deepseek/ 模块
├── dashboard.py  → 依赖 kernel, health, models
├── discovery.py  → 独立（只依赖缺胳膊 breakpath）
├── cli.py        → 依赖所有核心模块
└── server.py     → 依赖 handlers/*, deepseek/*

handlers/
├── system_routes.py  → 依赖 kernel, models, health, dashboard
├── model_routes.py   → 依赖 kernel, models, discovery
├── chat_routes.py    → 依赖 kernel, models, chat, deepseek/
└── page_routes.py    → 独立（只返回 HTML）

deepseek/
├── params.py     → 独立（纯数据类）
├── errors.py     → 独立（纯逻辑类）
├── parser.py     → 依赖 params
├── client.py     → 依赖 params, parser, errors
├── anthropic.py  → 依赖 params, parser, errors, client
├── router.py     → 依赖 params, client, errors
└── anthropic_router.py → 依赖 anthropic
```

关键观察：**没有循环依赖**。`kernel.py` 在最底层，所有模块都依赖它而不反过来依赖。这是设计的第一原则。

## 四、常见误区

### 4.1 「这是个 DeepSeek 专属工具」

**❌ 错误理解**: 代码里有 `deepseek/` 目录，所以只支持 DeepSeek。

**✅ 实际情况**: 核心模型管理完全基于 OpenAI 兼容 API。可以添加任意 API 提供商：
- 智谱 GLM
- 百川
- Ollama
- 本地 llama.cpp
- 私有 OpenAI 兼容端点

DeepSeek 目录是**额外的特化功能**，不是限制。不配置 DeepSeek 也一样用仪表盘和模型管理。

### 4.2 「这是个推理引擎」

**❌ 错误理解**: 名字叫「核心」，会不会跑模型？

**✅ 实际情况**: 纯管理工具，不运行任何推理。它管理的是**配置**而不是**进程**。模型运行由 Ollama / llama.cpp / API 提供商负责。

### 4.3 「需要完整微服务架构才能跑」

**❌ 错误理解**: FastAPI、后端、前端、数据库……看起来很重。

**✅ 实际情况**: 总计 4 个 pip 包，整个后端 15 个 Python 文件，前端是原生 HTML/CSS/JS 没有构建步骤。

### 4.4 「CLI 就够了，Web UI 是多余的」

**❌ 错误理解**: 所有操作都能在终端完成。

**✅ 实际情况**: CLI 适合批量/自动化操作，Web UI 适合日常监控和浏览。用户反馈「一张 Web 表单的可见度远超十个 CLI 演示」——模型状态一目了然比敲 `arc list` 高效得多。

## 五、贡献指南

1. **先读 kernel.py** — 理解 ModelConfig 是一切的基础
2. **不要引入新框架** — 核心原则是「4 个依赖」
3. **DeepSeek 特化新功能**放在 `deepseek/` 目录
4. **通用模型管理新功能**放在 `core/` 根目录
5. **CLI 和 API 功能要保持同步** — 新功能同时提供 CLI 命令和 Web UI
6. **测试** — 当前无正式测试框架，但核心功能改动后手动验证 `arc list`、`arc serve`、`curl /api/system`
