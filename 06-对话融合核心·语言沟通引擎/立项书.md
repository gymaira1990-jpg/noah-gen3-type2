# 立项书：诺亚语言沟通核心·对话融合引擎

> 所属项目: 诺亚三代·二型 (noah-gen3-type2)
> 子项目编号: 05
> 状态: 📝 方案设计
> 日期: 2026-05-23

---

## 一、为什么做

### 1.1 背景

诺亚三代二型目前拥有四个成熟模块：
- **01** 上下文管理组装系统（抽屉级联压缩）
- **02** Mnemosyne 记忆宫殿（记忆/向量/知识图谱）
- **03** 认知AI底座
- **04** 原铸诺亚二代一型（完整诺亚实例）

但所有模块目前都寄生在 Hermes Agent 的对话循环上。Hermes 负责：
- 接收用户消息
- 调用 LLM
- 执行工具
- 管理对话循环
- 流式输出

我们用四个模块给 Hermes 打了大量补丁（钩子、MCP、pre-clean、抽屉压缩），但始终是在别人的框架里「借壳」运行。这带来了三个不可持续的问题：

**1. 框架耦合风险** — Hermes 升级改 API → 我们的钩子全挂
**2. 无法实现核心设计意图** — Hermes 的消息管理方式（线性列表 + DeepSeek 摘要）与诺亚的三层上下文设计（抽屉级联 + 结构化事实 + 热度追踪）从根本上不同。我们永远是在「纠正」而非「设计」
**3. 「降智」根因不可控** — 当前对话内信息丢失、工具调用结果被压缩掉、记忆碎片化等问题，根因都在 Hermes 的对话循环层，我们在上层打补丁修不到根

### 1.2 灵感来源：OA 工单系统

诺亚语境中的「电报」= OA 工单系统（secretary.py），本质是一个 **TOKEN 压缩瓶颈**：

每条发给大模型的消息，先经过工单系统的精炼——只保留必要的内容、去掉噪声、结构化输出。用户强调这是「节省 TOKEN 的精华」。

本模块的核心设计哲学继承这一思想：**对话融合引擎是语言沟通的瓶颈层，所有进出 LLM 的信息必须经过它的精炼。**

### 1.3 目标

构建一个**独立于任何 Agent 框架的语言沟通核心**，接管：

| 能力 | 说明 |
|:----|:-----|
| **上下文内部循环** | 为每条消息组装精简上下文（抽屉级联），替代 Hermes 的线性列表 |
| **大模型沟通** | 直接调用 LLM（DeepSeek/其他），流式输出，重试，降级链 |
| **不降智** | 结构化事实摘要（非自由叙事） + 热度保护 + 纠正保护，确保关键信息不丢失 |
| **不丢对话** | 消息级即时持久化（SQLite/PG），树形 parent_id 结构，零数据丢失 |
| **记忆稳固** | 与 Mnemosyne 直接对接，每次对话自动提取/更新记忆 |
| **工具调用** | 执行引擎，先桥接到 Hermes 工具，远期自建 |
| **串联功能** | 整合 01/02/03/04 模块的产出，作为诺亚对话的主枢纽 |

### 1.4 核心命题

> 如何构建一个完全自主的语言沟通核心，让诺亚：
> 1. 每次对话都用自己设计的上下文结构（不是 Hermes 的）
> 2. 每条消息都即时持久化（永远不会丢）
> 3. 每个工具调用结果都受保护（不会被压缩吃掉）
> 4. 每个记忆都稳固写入（和 Mnemosyne 双向同步）
> 5. 出了问题自动降级到 Hermes 原生（零中断）

## 二、做什么

### 2.1 产出物

1. **对话融合引擎核心** — 独立 Python 模块，实现完整的对话循环（上下文组装 → LLM 调用 → 工具执行 → 记忆写入）
2. **Hermes 桥接层** — 作为安全网：新模块出问题时自动回退到 Hermes 原生对话，零中断
3. **MCP 服务** — 对外暴露对话核心能力（context_assemble / chat / tool_exec）
4. **OA 工单适配** — 继承 secretary.py 的 TOKEN 压缩瓶颈设计，作为可选通信模式
5. **技术说明书** — 完整设计文档

### 2.2 非目标（明确不做）

- ❌ **不替代 Hermes 的工具系统** — 初期工具执行桥接到 Hermes，远期再考虑自建
- ❌ **不替代 Hermes 的 Gateway** — 消息平台接入（Telegram/Discord）继续用 Hermes Gateway
- ❌ **不做 WebUI** — WebUI 是 05 模块的消费者，但不是本模块的直接产出
- ❌ **不重写 LLM Provider 适配器** — 复用 Hermes 的 provider 配置和密钥管理

### 3.2 对话循环（核心流程）

```
用户消息到达
    │
    ▼
┌────────────────────────────────────┐
│ ① 持久化: 写用户消息到 SQLite       │
│    消息树: parent_id = 上条助理消息  │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ② 上下文组装 (调用模块01)           │
│    输入: 当前会话全部原始消息        │
│    输出: 精简上下文 (<13K tok)      │
│    含: 抽屉摘要 + 最近N条原始消息    │
│         + TFC活跃卡 + 记忆注入      │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ③ Prompt 构建                      │
│    system = 灵魂+技能+规则          │
│    messages = system + context + 用户消息 │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ④ LLM 调用 (流式)                  │
│    Provider: DeepSeek (主)          │
│    Stream: SSE token-by-token       │
│    ├─ 响应含 tool_call → 进入⑤     │
│    └─ 响应纯文本 → 进入⑥           │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ⑤ 工具执行桥                       │
│    解析 tool_call → 调用 Hermes 工具│
│    结果回注 → 回到④ (继续LLM)       │
│    工具结果受保护 (protect_last_n)  │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ⑥ 持久化: 写完整助理回复到 SQLite   │
│    包括: 文本 + 工具调用记录        │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ⑦ 记忆同步 (调用模块02)            │
│    提取关键事实 → 写入 Mnemosyne    │
│    更新热度 → 热度衰减              │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│ ⑧ 输出到 Gateway                   │
│    SSE 流式结束 → 完整回复发送给用户│
└────────────────────────────────────┘
```

### 3.3 降智防御体系

「不降智」是本模块的第一设计约束。定义：**压缩后模型仍能给出和未压缩时间等质量的回答。**

| 防御层 | 做法 | 对应模块 |
|:------|:-----|:---------|
| **结构化事实摘要** | 摘要格式固定：目标/决策/文件变更/TFC引用/纠正记录。禁止自由叙事 | Tier2 MemoryButler |
| **热度保护** | 高频引用/频繁纠正的内容热度高，不会被压缩掉 | Tier1 TemperatureIndex |
| **纠正保护** | 含 `[PROTECTED:]` 或 `__HERMES_SOUL_PROTECTED__` 标记的消息永不被压缩 | ProtectionDetector |
| **最近N条保活** | `protect_last_n >= 10` 条原始对话保留，不做任何压缩 | context_assembler |
| **工具结果保护** | 工具执行结果在保护区内，不被摘要/修剪 | DedupEngine |
| **OA工单瓶颈** | 每条LLM请求前经工单级精炼——只保留必要内容 | OA模式可选 |

### 3.4 OA 工单模式（可选通信模式）

继承 secretary.py 设计哲学，提供一种 **TOKEN 压缩瓶颈**通信模式：

```
普通模式:
  用户消息 → [全量上下文] → LLM → 回复

OA 工单模式:
  用户消息 → [工单生成器精炼] → [精炼上下文] → LLM → [工单格式回复]
                      ↓
              节省 40-60% TOKEN
```

工单生成规则：
- 只保留与当前消息相关的上下文段落
- 工具调用结果自动压缩到 200 字以内
- 历史决策以 `[决策: XXX]` 单行格式引用
- 用户偏好以 `[用户: XXX]` 单行格式引用

### 4.2 关键设计决策

| 决策 | 方案 | 理由 |
|:----|:-----|:-----|
| 语言 | Python 3.12+ | 与模块01/02/03/04统一 |
| 持久化 | PostgreSQL（主）+ SQLite（备） | 主用PG（已有），SQLite做离线备 |
| LLM调用 | 直接调用 OpenAI 格式 API | 不依赖 Hermes，DeepSeek/Ollama 同一接口 |
| 工具执行 | 桥接到 Hermes (初期) → 自建 (远期) | 初期避免重写30+工具 |
| 流式输出 | SSE (Server-Sent Events) | 与 Hermes Gateway 兼容 |
| 降级 | 健康检查 → 透明回退到 Hermes | 零中断原则 |
| OA工单 | 可选模式，默认不启用 | 保留秘书处设计意图但不强制 |

### 4.3 与现有模块的关系

```
模块01 (上下文管理) ──→ 提供抽屉压缩+Tier3组装能力
模块02 (Mnemosyne)  ──→ 提供记忆存储/检索/更新
```

## 五、开发路径

### Phase 1: 对话循环 MVP（方案设计完成后，1-2天）

实现核心循环的骨架：
- 消息持久化（PG 写入）
- 上下文组装（调用模块01的 Tier3 assemble）
- LLM 直接调用（DeepSeek API，流式）
- 工具桥接（调用 Hermes 执行工具）
- 降级开关（健康检查 → Hermes 回退）

验证：Man-in-the-middle 模式——Hermes 正常跑，05模块作为观察者同步运行，对比输出质量和 TOKEN 消耗。

### Phase 2: 记忆同步（+1天）

- 每次对话后触发 Mnemosyne 记忆写入
- 热度更新和衰减
- 纠正提取和归档

### Phase 3: OA 工单模式（+1天）

- 工单生成器实现
- 工单模式开关
- TOKEN 节省统计

### Phase 4: 自建工具执行（远期）

等 Phase 1-3 稳定运行后评估是否需要。

## 六、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|:----|:----:|:----:|:-----|
| LLM 直接调用接入复杂 | 中 | 延误 | 复用 Hermes provider 配置 |
| 工具桥接不稳定 | 中 | 功能受限 | 早期只桥接核心工具（5-10个） |
| 与 Hermes 双轨运行时上下文不一致 | 高 | 混淆 | Phase 1 只观察不干预 |
| 抽屉压缩在真实对话中效果不达标 | 中 | 降智 | 结构化事实兜底 + protect_last_n 保活 |
| 模块01/02 接口变更 | 低 | 需适配 | 锁定版本依赖 |

## 七、判断标准

本模块成功上线标志：

- [ ] 诺亚对话完全通过 05 模块运行（不经过 Hermes ContextCompressor）
- [ ] 连续 100 轮对话零数据丢失
- [ ] 降级触发时用户无感知（Hermes 透明接管）
- [ ] OA 工单模式节省 TOKEN ≥ 40%（对比 Hermes 原生）
- [ ] 工具调用正确执行率 ≥ 99%
