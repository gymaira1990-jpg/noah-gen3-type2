# 方案设计 01：对话循环设计

> 所属模块: 05-对话融合核心·语言沟通引擎
> 版本: v0.1 (方案)
> 日期: 2026-05-23

---

## 1. 问题定义

Hermes 当前的对话循环（`AIAgent.run_conversation()`）是一个黑盒：
- 消息以线性列表管理
- 压缩触发阈值固定（50% / 750K tokens）
- 压缩=DeepSeek语义摘要（付费模型，每次几千token）
- 外部无法干预上下文组装策略

本模块的目标是**接管对话循环的控制权**，但不接管 LLM 调用和工具执行的底层实现。

## 2. 循环模型

### 2.1 核心抽象

```
ConversationEngine
├── state: ConversationState (当前会话全部状态)
├── loop(): 主循环
│   ├── receive(message)     → 接收用户消息
│   ├── persist(message)     → 写入持久层
│   ├── assemble_context()   → 调用模块01产出精简上下文
│   ├── build_prompt()       → 系统提示+上下文+用户消息
│   ├── call_llm()           → 流式调用，处理tool_call
│   ├── execute_tool()       → 桥接到Hermes或自建执行
│   ├── persist(response)    → 写入持久层
│   ├── sync_memory()        → 同步到模块02
│   └── return(output)       → 返回给Gateway
└── fallback: HermesEngine   → 降级时透明切换
```

### 2.2 状态模型

```python
@dataclass
class ConversationState:
    session_id: str               # 会话ID（与Hermes Gateway对齐）
    messages: List[Message]       # 全部原始消息（永不删除）
    context: CompressedContext     # 当前精简上下文（模块01产出）
    memory: MemorySnapshot         # 当前记忆快照
    tfc_cards: List[TFCCard]       # 活跃TFC卡
    health: EngineHealth           # 健康状态

@dataclass  
class Message:
    id: int
    role: str                      # user / assistant / tool
    content: str | List[ContentPart]
    parent_id: int | None          # 树形结构
    created_at: datetime
    meta: dict                     # tokens, tool_calls, latency等
```

### 2.3 关键设计约束

**1. 消息永不删除** — 原始消息列表是事实源。压缩上下文只是精炼后的视图，不替代原始数据。

**2. 上下文 = 快照，不是替换** — `assemble_context()` 每次从原始消息列表重新生成精简上下文，不做增量更新（避免增量更新导致的错误累积）。

**3. 压缩 ≠ 摘要** — 压缩是「结构化精简」（抽屉级联），不是「语义重写」（Hermes的方式）。保留原文片段 + 结构化事实，不创造新的叙事。

## 3. 数据流

```
                      原始消息列表 (永不删除)
                      ├── msg_1: user   "帮我查下服务器"
                      ├── msg_2: tool   "连接成功"
                      ├── msg_3: assistant "服务器IP是..."
                      ├── msg_4: user   "帮我部署"
                      ├── msg_5: tool   "部署完成"
                      ├── ...

                              │

                     └── 组装 (ContextAssembler.assemble)

                              │
                              ▼
                     ┌──────────────────────┐
                     │  精简上下文 (<13K tok) │
                     │                      │
                     │  抽屉摘要（结构化事实）  │
                     │  - 活跃目标            │
                     │  - 已做决策            │
                     │  - 文件变更            │
                     │  - TFC引用            │
                     │  - 纠正记录            │

                     │                      │
                     │  记忆注入              │

```

## 4. LLM 调用协议

设计为 OpenAI chat completions 格式，与 DeepSeek/Ollama 原生兼容。

```python
class LLMCommunicator:
    def __init__(self, provider_config: ProviderConfig):
        self.client = OpenAI(
            base_url=provider_config.base_url,
            api_key=provider_config.api_key
        )
    
    async def stream_chat(
        self,
        messages: List[dict],
        tools: List[dict] | None,
        temperature: float = 0.7
    ) -> AsyncIterator[StreamEvent]:
        """
        流式调用LLM，产出三种事件：
        - StreamEvent.TOKEN:    普通文本token
        - StreamEvent.THINK:    思考过程token
        - StreamEvent.TOOL_CALL: 工具调用请求
        """
```

### 4.1 流式事件协议

```python
@dataclass
class StreamEvent:
    type: Literal["token", "think", "tool_call", "done", "error"]
    content: str | None
    tool_calls: List[ToolCall] | None
    
    @dataclass
    class ToolCall:
        id: str
        type: str                    # "function"
        function: FunctionCall
    
    @dataclass
    class FunctionCall:
        name: str
        arguments: str               # JSON string
```

### 4.2 重试策略

| 错误类型 | 重试次数 | 间隔 | 降级 |
|:---------|:-------:|:----:|:-----|
| 连接超时 (timeout) | 2 | 3s, 6s | 切备用 provider |
| 认证失败 (401) | 0 | — | 切备用 provider |
| 速率限制 (429) | 3 | 10s, 20s, 40s | 等待 |
| 服务端错误 (500+) | 2 | 5s, 10s | 切备用 provider |
| 上下文超长 (413) | 1 | 压缩后重试 | 强制压缩 |

## 5. 持久化模型

### PostgreSQL Schema

```sql
CREATE TABLE conversation_sessions (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title       TEXT,
    platform    TEXT NOT NULL DEFAULT 'cli',    -- cli / telegram / discord
    platform_uid TEXT,                          -- 平台用户ID
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    meta        JSONB                           -- 会话元数据
);

CREATE TABLE conversation_messages (
    id          BIGSERIAL PRIMARY KEY,
    session_id  UUID NOT NULL REFERENCES conversation_sessions(id),
    role        TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool', 'system')),
    content     JSONB NOT NULL,                 -- 支持多模态内容
    parent_id   BIGINT REFERENCES conversation_messages(id),
    tool_calls  JSONB,                          -- assistant消息的工具调用请求
    tool_result JSONB,                          -- tool消息的执行结果
    tokens_in   INT,                            -- 输入token数
    tokens_out  INT,                            -- 输出token数
    model       TEXT,                           -- 使用的模型
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_messages_session ON conversation_messages(session_id, created_at);
CREATE INDEX idx_messages_parent ON conversation_messages(parent_id);
```

### 写入铁律

**用户消息 + 助理回复必须在同一次请求内完成写入，不存在「发了消息但没收到回复」的中间状态。** 实现方式：

```python
async def process_message(user_msg: str) -> None:
    async with db.transaction():
        # 1. 写入用户消息
        user_msg_id = await db.execute(
            "INSERT INTO conversation_messages (...) VALUES (...)"
        )
        # 2. 调用LLM（流式）
        full_response = ""
        async for event in llm.stream():
            # 实时写入每个chunk（SSE用）
            if event.type == "token":
                full_response += event.content
        # 3. 写入完整助理回复
        await db.execute(
            "INSERT INTO conversation_messages (...) VALUES (...)"
        )
    # 事务提交 → 用户消息和助理回复同时可见
```

## 7. 关键陷阱

### 陷阱1：消息ID冲突
PG bigserial 在跨会话时不会冲突（不同 session_id），但同一 session 内的 parent_id 引用必须是在同一连接/事务内生成的。不要先INSERT再查询ID——用 `RETURNING id`。

### 陷阱2：SSE与事务的死锁
如果在 SSE 流式输出过程中持有数据库事务锁，长时间流式输出期间会锁定表。**解决方案**：每条消息写入使用独立短事务，流式输出过程不持有事务。

### 陷阱3：tool_call 的循环深度
LLM 在一次回复中可能调用多个工具（并行），且工具结果回注后 LLM 可能继续调用新工具。必须设置最大工具调用深度（建议 10 轮），避免无限循环。

### 陷阱4：上下文组装频率
`assemble_context()` 是模块01的核心调用，每次对话轮都调一次。如果消息量 < protect_last_n，则直接返回最近N条消息，跳过完整的抽屉压缩流程（优化路径）。
