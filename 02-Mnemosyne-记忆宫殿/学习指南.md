## 三、核心算法

### 3.1 热度计算

热度不是单一的「访问次数」，而是三维加权：

```python
async def update_heat_score(conn, memory_id: int):
    """三维热度计算"""
    memory = await conn.fetchrow(
        "SELECT access_count, last_accessed, importance FROM memories WHERE id=$1",
        memory_id
    )
    
    # 维度 1: 访问频率 (归一化到 0~1)
    freq_30d = min(memory['access_count'] / 100, 1.0)
    
    # 维度 2: 新鲜度 (越近越热)
    days_since = (datetime.utcnow() - memory['last_accessed']).days
    recency = max(0, 1 - days_since / 30)  # 30 天归零
    
    # 维度 3: 重要性 (用户反馈)
    importance = memory['importance']
    
    # 融合
    heat = 0.4 * freq_30d + 0.35 * recency + 0.25 * importance
    
    # 更新
    tier = 'L1' if heat > 0.7 else 'L2' if heat > 0.2 else 'L3' if heat > 0.05 else 'L4'
    await conn.execute(
        "UPDATE memories SET heat_score=$1, tier=$2 WHERE id=$3",
        heat, tier, memory_id
    )
```

**为什么三维？** 单一维度的缺陷：
- 只看频率：一条被频繁问但已不重要的旧知识仍很热
- 只看新鲜度：刚存的寒喧比上周存的重要决策更热
- 只看重要性：用户标记了重要但再也没问过的知识占位置

三维融合 = 频率 + 新鲜度 + 重要性，互相制衡。

### 3.2 四维检索

语义搜索为主，多维补充：

```python
async def search(user_id: str, query: str, top_k: int = 5):
    # 1. 生成查询向量
    embedding = await get_embedding(query)
    
    # 2. 语义搜索 (pgvector HNSW)
    semantic_results = await conn.fetch("""
        SELECT id, content, heat_score, 
               embedding <=> $1::vector AS distance
        FROM memories
        WHERE user_id = $2 AND is_deleted = false
          AND tier NOT IN ('L4')
        ORDER BY distance ASC
        LIMIT $3
    """, embedding, user_id, top_k * 2)
    
    # 3. 关键词补充 (pg_trgm ILIKE)
    keyword_results = await conn.fetch("""
        SELECT id, content, heat_score
        FROM memories
        WHERE user_id = $1 AND is_deleted = false
          AND content ILIKE '%' || $2 || '%'
        ORDER BY heat_score DESC
        LIMIT $3
    """, user_id, query, top_k)
    
    # 4. 融合排序 (语义结果优先 + 关键词补充)
    return fuse_results(semantic_results, keyword_results, top_k)
```

**融合策略**：
- 语义搜索命中且距离 < 0.5 的排最前
- 语义搜索命中但距离 > 0.5 的次之
- 纯关键词命中的排最后（防止数量淹没语义）
- 重复结果去重

## 四、关键设计决策

### 为什么 MCP 协议？

MCP (Model Context Protocol) 是 Anthropic 推出的 AI 工具标准。用 MCP 的好处：
- 任意兼容客户端零适配接入（Claude Desktop / Hermes / 自研框架）
- 工具定义即文档（JSON Schema 自动生成文档）
- stdin/stdout 传输，不需要 HTTP（但 Mnemosyne 用了 HTTP 模式更可靠）

### 为什么 asyncpg 而不是 psycopg2？

Mnemosyne 核心是 I/O 密集（数据库查询 + HTTP 调 Ollama），不是 CPU 密集。asyncpg 的异步非阻塞在等待数据库/HTTP 响应时能处理其他请求。PS: psycopg2 同步版在 FastAPI 里会用线程池兜底，但不如 asyncpg 优雅。

### 为什么四层热度而不是二进制？

二进制（热/冷）太粗糙。一个刚降级的「常温」记忆和一个近乎遗忘的「冷」记忆混在一起——搜索时无法区分优先级。四层 = 四个粒度，从「自动注入」到「几乎要删」。

### 为什么软删除？

记忆删除后可能还需要：审计追踪、用户后悔恢复、分析「什么被遗忘了」。硬删除 = 丢失所有信息。软删除 = 保留 30 天后再物理清理。

### 5.1 FastAPI 路由注册陷阱

静态路径必须在动态路径之前注册：

```python
# ❌ 错误: 动态路径先注册
@app.get("/memories/{memory_id}")     # 会匹配 /memories/heat-top
@app.get("/memories/heat-top")        # 永远不会到达这里

# ✅ 正确: 静态路径先注册  
@app.get("/memories/heat-top")
@app.get("/memories/{memory_id}")
```

## 六、常见误解

### ❌ "Mnemosyne 自己做视觉理解"

**不是。** Agent 的多模态模型（如 GLM-4.6V-Flash）理解图片后，把文本描述传给 Mnemosyne 存。Mnemosyne 只存文本，不做理解。

### ❌ "Mnemosyne 可以替代对话模型"

**不能。** Mnemosyne 是记忆系统，不是推理系统。它不能替代 Agent 的对话生成——它只是让 Agent 有个地方存/取记忆。

### ❌ "部署 Mnemosyne 需要从头装所有依赖"

**不用。** 如果服务器上已有 Ollama + PostgreSQL，只需装 FastAPI + asyncpg + httpx。三小只（Ollama/Reranker/LLMLingua）已就绪就只需建库建表。

### ❌ "四维检索的图遍历是必须的"

**不是必须的。** Apache AGE 图数据库是可选高级功能。前三维（语义+关键词+时序）已覆盖 95% 的检索需求。图遍历只在多跳实体查询场景需要（如「找到和 X 有关的所有人」）。
