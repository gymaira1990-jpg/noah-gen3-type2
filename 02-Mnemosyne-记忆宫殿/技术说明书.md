# Mnemosyne 记忆宫殿 · 技术说明书

> **一个独立于 Agent 框架的外挂记忆系统。AI 智能体通过 MCP 协议调用，提供永久记忆与知识检索。**
>
> 版本: v3.0 · 2026-05-22 · 状态: ✅ 生产就绪
> 代码量: ~3,500 行 · 工具数: 33 个 MCP 工具 · 数据表: 13 张

---

## 一、痛点

### 1.1 Agent 的记忆困境

大模型 Agent 有两个「脑子」：

1. **上下文窗口**（短暂记忆）—— 对话期间的短期记忆，压缩即失忆
2. **知识库**（长期记忆）—— 固化的事实和文档，但搜索慢、更新麻烦

缺一个「中程记忆」—— 不是对话上下文（太短暂），不是知识库（太固化），而是「Agent 自己经历过的、未来可能用到的」记忆。

```
上下文窗口        ← 几轮对话后就没了
    ↓ 压缩 90%
知识库            ← 知识库需要手动维护
    ↓
缺的: 外挂记忆     ← Agent 自己读、自己写、自己遗忘
```

### 1.2 为什么不做在本地？

本地已有的 Hermes Agent 有 memory_store 和 memory_recall 工具，但：

- 本地内存有限，存不了太多
- 跨会话记忆依赖 SQLite，不适合向量搜索
- 不是独立服务，Agent 重启记忆就丢

**解决方案**：把记忆做成独立的外挂系统——完全独立的服务器、独立的数据库、独立的进程，Agent 通过 MCP 协议远程调用。

### 1.3 设计哲学

```
HERMES 是主脑，Mnemosyne 是外挂硬盘。

HERMES 负责:
  - 对话生成（推理）
  - 视觉理解（智谱 GLM-4.6V-Flash）
  - 工具编排（MCP 调用）
  - 上下文管理（抽屉级联压缩）

Mnemosyne 负责:
  - 永久记忆存储（文本 + 多模态）
  - 四维检索（语义 + 关键词 + 时序 + 图）
  - 热度遗忘（自动衰减 + 分层）
  - 自我进化（去重 + 合并 + 实体提取 + 冲突检测）
```

## 二、系统架构

```
AI Agent (本地)
    │ MCP 协议 (通过 SSH 隧道)
    ▼
┌──────────────────────────────────────────────────┐
│  Nginx (:443) — HTTPS + Token 认证 + IP 白名单   │
├────────────────┬────────────────┬───────────────┤
│  MCP Server    │  FastAPI 引擎  │  Reflector     │
│  (工具桥接层)   │  (:8010)      │  (cron 定时)   │
│  (:8001)       │  核心 CRUD     │  light/deep    │
│                │  四维检索      │  去重合并      │
│                │  热度更新      │  实体提取      │
├────────────────┴────────────────┴───────────────┤
│  ┌──────────┐  ┌──────────┐  ┌──────────────┐   │
│  │Ollama    │  │Reranker  │  │LLMLingua     │   │
│  │:11434    │  │:11436    │  │:11437        │   │
│  │向量化     │  │重排序    │  │压缩          │   │
│  └──────────┘  └──────────┘  └──────────────┘   │
├─────────────────────────────────────────────────┤
│  PostgreSQL 16 + pgvector + pg_trgm + AGE       │
│  mnemosyne 数据库 (13 张表)                      │
└─────────────────────────────────────────────────┘
```

### 核心设计原则

1. **独立部署** — 完全独立的服务器 + 数据库 + 进程，不依赖本地任何组件
2. **不做推理** — Mnemosyne 只做记忆，不做对话、不搞路由、不负责视觉理解
3. **从零开始** — 独立数据库，不迁移已有数据
4. **MCP 标准** — 全 MCP 协议，任意兼容客户端零适配接入
5. **渐进增强** — 核心先行，后续逐步添加图谱/高级进化

## 三、热度分层遗忘

### 3.1 三维热度公式

```
Heat_Score = 0.4 × normalized(Freq30d) 
           + 0.35 × (1 - normalized(RecencyDays)) 
           + 0.25 × Importance
```

| 维度 | 权重 | 含义 |
|:-----|:----:|:-----|
| 访问频率 | 40% | 最近 30 天被访问次数，归一化到 [0,1] |
| 新鲜度 | 35% | 越近越热，未访问时间越长越冷 |
| 重要性 | 25% | 用户反馈的重要性标记 (0~1) |

### 3.2 四层热度分层

| 层级 | 阈值 | 行为 | 存储位置 |
|:-----|:----:|:-----|:---------|
| 🔥 L1 热 | > 0.7 | 全量注入上下文 | 高优先级检索 |
| 🌤 L2 常温 | 0.2 ~ 0.7 | 普通检索命中 | 主表活跃区 |
| ❄ L3 冷 | 0.05 ~ 0.2 | 低优先级检索 | 主表，频率降低 |
| 🧊 L4 归档 | < 0.05 | 不参与检索 | 保留在表中可手工恢复 |

### 3.3 日常衰减

```
每日 cron 执行:
  UPDATE memories SET heat_score = heat_score * 0.95
  WHERE is_deleted = false
```

## 四、四维检索

| 维度 | 技术 | 适用场景 |
|:-----|:-----|:---------|
| 语义 | pgvector HNSW (cosine) | 自然语言问句匹配 |
| 关键词 | pg_trgm ILIKE | 精确术语/编号搜索 |
| 时序 | SQL ORDER BY last_accessed | 最近访问记录 |
| 图遍历 | Apache AGE (Cypher) | 实体关联多跳查询 |

检索策略：**语义优先，多维度融合**。语义搜索为主要入口，命中不足时补充关键词和时序，图遍历为高级模式（可选）。

## 七、存储引擎链

```
写入链:
Agent → memory_store (MCP) → FastAPI → 生成 embedding (Ollama :11434)
                                        → 写入 PG mnemosyne
                                        → 更新 memory_traces

检索链:
Agent → memory_recall (MCP) → FastAPI → HNSW 向量搜索 (pgvector)
                                        → Reranker 重排序 (:11436, 可选)
                                        → 关键词补充 (pg_trgm)
                                        → 融合排序后返回

遗忘链:
cron (每天) → Reflector → 热度衰减 (heat_score × 0.95)
                          → L4 归档标记 (heat_score < 0.05)
                          → 重复检测 (cosine_sim > 0.92 合并)
                          → 实体提取 (deep 模式)
```
