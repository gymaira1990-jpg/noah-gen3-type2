## 三、实现策略
## ════════════════════════════════════════════

### 3.1 是否要全做？

| | 方案A：全实现 | 方案B：核心先行 | 方案C：渐进进化 |
|---|---|---|---|
| 范围 | 8份蓝图92个组件 | URR + 自动调优 + 记忆升级 | 先URR，再按需添加 |
| 代码量 | ~5000行新增 | ~1500行新增 | ~800行新增 |
| 风险 | 高(过度工程) | 中 | 低 |
| 价值 | 完整数字基座 | 解决核心痛点(幽灵数据+路由调优) | 解最急的问题 |

**推荐：方案B → 渐进到方案A**

先解决最痛的点：
- **URR** → 杜绝幽灵数据（核心关切）
- **api_call_log增强** → 调用记录可追踪
- **自动调优** → 路由自己变聪明
- **记忆升级** → 热度引擎+四库分离

工具模块、基础设施层的插件/事件总线等，在核心跑稳后再逐步加入。

### 3.2 实施顺序（细化）

```
Phase 1: URR 基建           → 当前焦点 (2-3会话)
Phase 2: 调用日志增强+指标   → Phase 1之后 (1-2会话)  
Phase 3: 自动调优           → Phase 2之后 (2会话)
Phase 4: 记忆系统升级       → Phase 3之后 (2-3会话)
Phase 5: 工具管理模块       → 可选 (3-4会话)
Phase 6: 基础设施           → 可选，按需
```
