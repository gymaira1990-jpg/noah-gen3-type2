### 2.1 融合原则

1. **不动P4 Router核心** — 路由引擎、降解链、向量匹配是原铸的成熟资产，只做增强不做重写
2. **URR作为新层叠加** — 不侵入现有路由逻辑，通过 Adapter 模式对接现有资源
3. **api_call_logs 增量升级** — 保留现有表结构，加列不删列
4. **自动调优渐进启用** — 先收集数据再优化，不跳步

## 三、Phase 1：统一资源注册中心 (URR)
## ════════════════════════════════════════════

### 3.1 新增表

```sql
-- 核心资源注册表
CREATE TABLE resource_registry (
    resource_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    resource_type VARCHAR(50) NOT NULL,   -- model | api_key | project | memory | tool | service
    resource_subtype VARCHAR(50),          -- deepseek-v4 | doubao | ollama | archive | general
    name VARCHAR(255) NOT NULL,
    description TEXT,
    status VARCHAR(20) DEFAULT 'active',  -- active | deprecated | archived | deleted
    data_table VARCHAR(100),              -- 实际数据所在的表名
    data_id VARCHAR(100),                 -- 实际数据在表中的ID
    tags TEXT[] DEFAULT '{}',
    metadata JSONB DEFAULT '{}',
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    deprecated_at TIMESTAMP,
    archived_at TIMESTAMP,
    deleted_at TIMESTAMP,
    UNIQUE(data_table, data_id)
);

-- 资源关系表
CREATE TABLE resource_relations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_resource_id UUID NOT NULL REFERENCES resource_registry(resource_id),
    target_resource_id UUID NOT NULL REFERENCES resource_registry(resource_id),
    relation_type VARCHAR(50) NOT NULL,  -- references | depends_on | belongs_to | uses | generates
    metadata JSONB DEFAULT '{}',
    created_at TIMESTAMP DEFAULT NOW()
);
```

## 五、Phase 3：自动调优引擎 (AutoOptimizer)
## ════════════════════════════════════════════

### 5.1 核心逻辑

```
cron(每30分钟):
  1. 读取最近7天的 provider_metrics
  2. 对每个provider+task_type计算综合评分:
     score = α*(1-error_rate) + β*(1-latency_pctile) + γ*(1-cost_rel)
     α=0.4, β=0.35, γ=0.25  (可配置)
  3. 更新 DegradationChain 中各 provider 的运行时权重
  4. 生成调优报告
```

### 5.2 实现位置

- `p4_router/optimizer/__init__.py` — AutoOptimizer 核心
- `p4_router/optimizer/metrics_aggregator.py` — 聚合任务
- 作为 Hermes cron job 独立运行

### 5.3 安全机制

| 机制 | 说明 |
|------|------|
| 最小样本量 | provider在过去24小时少于10次调用时不做权重调整 |
| 熔断保护 | error_rate > 50% 直接摘除不参与路由（已有） |
| 人工覆盖 | Admin API /toggle 手动标记优先级始终高于自动调优 |
| 回滚存档 | 每次调优前自动存当前权重快照 |

## 六、Phase 4：记忆系统升级 + GhostData 对接
## ════════════════════════════════════════════

### 6.1 memory_store 升级

```sql
ALTER TABLE memory_store ADD COLUMN IF NOT EXISTS heat_score REAL DEFAULT 50.0;
ALTER TABLE memory_store ADD COLUMN IF NOT EXISTS tier VARCHAR(20) DEFAULT 'warm';  -- hot/warm/cold/warehouse
ALTER TABLE memory_store ADD COLUMN IF NOT EXISTS access_count INT DEFAULT 0;
ALTER TABLE memory_store ADD COLUMN IF NOT EXISTS last_accessed TIMESTAMP DEFAULT NOW();
ALTER TABLE memory_store ADD COLUMN IF NOT EXISTS resource_id UUID REFERENCES resource_registry(resource_id);
```

### 6.2 热度引擎

```
每4小时 cron:
  对每条 memory_store:
    heat_score = 0.6 * exp(-(now - last_accessed)/decay_constant) 
               + 0.4 * normalize(access_count / 7d)
    
    if heat_score > 70: tier = 'hot'
    elif heat_score > 40: tier = 'warm'
    elif heat_score > 10: tier = 'cold'
    else: tier = 'warehouse'
    
    if tier = 'warehouse' AND last_accessed > 90天: → 标记待销毁,30天宽限期
```

### 6.3 GhostData 对接

每个 memory 写入/更新时自动调用 URR：
- 检查引用的资源是否 active
- 如引用已废弃/删除 → 告警并阻止写入
- 写入 URR 注册记录

## 七、Phase 5：健康探测 + 语义缓存
## ════════════════════════════════════════════

### 7.1 健康探测

```
新增 p4_router/probes.py:
  每60秒：
    for each provider:
      发送小型探测请求（~10 tokens）
      记录响应时间/状态码
      if 连续3次超时 OR error_rate > 30%:
        → 自动标记 dead
        → Admin API 可查看到探测日志
```

### 7.2 语义缓存（高级，可选）

```
利用现有的 route_vectors 表：
  查询时先计算 prompt 的 embedding
  在 route_vectors 中搜索相似查询 (cosine > 0.95)
  如命中缓存 → 直接返回缓存结果，不走模型
  如未命中 → 走路由，将结果写入缓存
```
