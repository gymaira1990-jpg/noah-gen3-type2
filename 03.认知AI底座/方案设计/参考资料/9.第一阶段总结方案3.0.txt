# 数字AI基座（Digital AI Base）完整设计方案 v3.0

## 一、概述

**数字AI基座**是一个通用、可扩展的个人AI智能体核心系统，提供模型统一路由、工具统一管理、认知记忆底座、电报/回复单协议、STC自我进化等核心能力。所有需要AI能力或工具的地方，都通过统一的中台进行调度和管理，实现“一个入口，所有能力”。

**设计原则**：
- **一切皆资源，一切需注册**：模型、工具、记忆、项目、API Key等均为统一管理的资源。
- **架构强制而非提示词请求**：通过电报协议、质检验收、调用日志等方式从架构层面保证输出质量和行为可控。
- **标准化与可扩展**：借鉴MCP等开放协议，工具接入标准化，支持热插拔和社区生态复用。
- **自我进化闭环**：成功的电报和工具使用经验自动沉淀为STC能力，越用越强。

各层职责：
- **API管理模块**：AI模型的唯一调用入口，管理所有大模型连接器，提供统一的`/gateway/chat`接口，负责路由、降级、健康监控、调用日志和自动调优。
- **工具管理模块**：工具的唯一调用入口，管理所有本地和外部工具（搜索、文件、代码执行等），提供统一的`/gateway/tool`接口，支持MCP协议实现工具的标准化接入。
- **认知记忆底座**：包含记忆引擎（四库记忆+项目中心）、热度引擎（双权重计算+四级流转）、电报引擎（TEL组装+MAIL解析）、STC进化、去重、索引、校验等。负责组装任务电报，调用API和工具模块，并将结果沉淀为记忆和技能。
- **数据与基础设施层**：PostgreSQL+pgvector双库引擎（真相与索引分离），配置管理、事件总线、可观测性、插件系统等。

## 三、核心协议：电报/回复单（TEL/MAIL）

### 3.1 电报（TEL）标准格式

电报是认知记忆底座与API管理模块之间唯一的通信协议，确保所有AI调用都经过结构化的任务描述和事实基础。

```xml
<TEL>
<CONTRACT>
你是一个任务执行器，你的工作分两步：
1. 组织相关行业专家（如果需要），基于下面提供的事实给出初步答案。
2. 启动一个内部的“质检验收团队”，对初步答案逐项核查。

质检验收团队的核查清单（必须全部通过）：
- [ ] 本地核对：答案是否完全基于本电报的 <FACTS> ？不得引入未列出的本地信息。
- [ ] 项目进度核对：答案是否考虑了 <PROGRESS> ？若有冲突必须指出。
- [ ] 网络核对：涉及的外部知识（版本号、参数、日期等）是否与电报中提供的网络检索摘要一致？若无摘要则标记“未核实”。
- [ ] 完成度检查：答案是否直接解决了 <TASK> ？是否提供了可执行的下一步？
- [ ] 归档登记：指明“本答案已核实，建议归档至[知识馆/项目中心]路径X”。

关键规则：
- 所有核查通过，status 填 "SUCCESS"，并在 evidence 字段中简要说明每项核查结果。
- 任一核查不通过，status 必须填 "NEED_MORE_INFO"，在 uncertainties 中列出未通过项及缺失信息，禁止输出完整答案，只能返回核查失败的状态和原因。
- 如果回答需要外部工具（如网络搜索），请在 uncertainties 中明确请求，系统将调用工具后重新发送本电报。
</CONTRACT>
<TASK>{用户任务描述}</TASK>
<REQUIREMENTS>{具体要求，如输出格式、语气等}</REQUIREMENTS>
<FACTS>{从记忆库、项目中心、工具调用结果中提取的已核实事实}</FACTS>
<REFERENCES>{相关历史工单或文档引用}</REFERENCES>
<PROGRESS>{当前项目进度、上次完成情况}</PROGRESS>
<NOTES>{额外提醒或约束}</NOTES>
</TEL>
```

### 3.2 回复单（MAIL）标准格式

API管理模块必须返回以下JSON格式的回复单：

```json
{
  "status": "SUCCESS | PARTIAL | FAILED | NEED_MORE_INFO",
  "result": "核心答案，禁止废话",
  "evidence": "逐项核查结果说明",
  "uncertainties": "未通过的核查项或不确定内容，若无则填'无'",
  "suggestions": "改进建议或需要补充的信息，若无则填'无'"
}
```

**回复单处理流程**：
1. 解析MAIL JSON，检查必填字段和status枚举值。
2. 若status为`NEED_MORE_INFO`，提取缺失信息，自动补充检索（调用工具模块）并重新组装电报递归调用，最多重试2次；仍失败则向用户请求补充信息。
3. 若status为`SUCCESS`，用本地模型校验`result`与`FACTS`的一致性（如发现不一致，标记为`NEED_MORE_INFO`重试）。
4. 通过后，将`result`存储为常规记忆工单，并依据`evidence`中的归档路径写入对应记忆库。
5. 将完整的TEL和MAIL存入`telegrams`和`mails`表，作为STC进化的数据基础。

## 四、API管理模块（大模型统一路由）

### 4.1 设计要点

- **唯一的AI能力提供方**：所有需要AI模型的模块（认知记忆底座、工具模块等）都必须通过API管理模块调用模型，不直接访问模型API。
- **一个模型一个专属连接器**：为每个模型深度定制参数、电报风格和解析方式。
- **统一调用日志**：记录每次调用的调用者、参数、结果、成本、质量评分等，为自动调优提供数据基础。

### 4.2 模型连接器基类

```python
class BaseModelConnector(ABC):
    def __init__(self, model_id: str, client, metrics: ModelMetrics):
        self.model_id = model_id
        self.client = client
        self.metrics = metrics

    @abstractmethod
    def build_tel(self, task: str, facts: str, context: dict) -> str:
        """为该模型定制电报格式"""
        ...

    @abstractmethod
    def build_request_params(self, tel: str) -> dict:
        """定制API请求参数（含专属参数，如response_format等）"""
        ...

    @abstractmethod
    def parse_response(self, raw_response) -> dict:
        """从原生返回中解析出标准MAIL JSON"""
        ...

    def record_call(self, success: bool, latency_ms: float, tokens: int):
        """更新热度指标"""
        ...
```

### 4.3 已支持的模型及专属配置

#### DeepSeek Chat 连接器

- **策略**：JSON模式，低温度减少幻觉。
- **参数**：`response_format: {"type": "json_object"}`, `temperature: 0.1`, `top_p: 0.95`, `max_tokens: 4096`。
- **解析**：清理可能的```json包裹层。

#### 豆包系列连接器

- **策略**：利用严格JSON Schema和服务器缓存。
- **参数**：`response_format: {"type": "json_schema", "json_schema": {...}, "strict": true}`, `enable_cache: true`, `cache_ttl: 3600`。
- **解析**：直接JSON解析。

#### 本地Ollama连接器（Qwen系列）

- **策略**：纯文本模式，简单包装为MAIL。
- **参数**：`temperature: 0.1`, `options: {num_predict: 2048, ...}`。
- **解析**：将纯文本包裹为简单MAIL。

### 4.4 智能路由与降级链

**路由决策顺序**：
1. 用户显式指定模型 → 直接使用。
2. 场景工作台配置的默认模型。
3. 意图分类：简单闲聊 → 本地模型；复杂任务 → API模型。
4. 同优先级按热度分排序（成功率 × 最近调用衰减因子）。
5. 健康过滤：跳过熔断或余额不足模型。
6. 降级链：DeepSeek Chat（主）→ 豆包Lite（备用）→ 豆包Pro（强力后备）→ 本地Qwen（兜底）。

### 4.5 统一调用接口

```python
class APIGateway:
    async def call(self, request: APIRequest) -> APIResponse:
        # 1. 记录调用开始（call_log）
        # 2. 路由选择模型
        # 3. 根据连接器构建请求并发送
        # 4. 记录调用结果（延迟、Token、成本）
        # 5. 更新模型热度指标
        # 6. 返回MAIL
```

### 4.6 调用日志与自动调优

- **调用日志表**：`api_call_log`（caller, model_id, request_type, params, response_status, latency, tokens, cost, quality_score等）。
- **自动调优引擎**：定期分析调用日志，按任务类型-模型维度统计质量、成本、延迟，自动调整路由权重和默认参数（如temperature）。

## 五、工具管理模块（感官与四肢中枢，MCP兼容）

### 5.1 设计要点

- **工具的唯一调用入口**：所有模块通过`/gateway/tool`调用工具，不直接访问工具。
- **标准化的工具接入**：内置MCP协议支持，工具提供方只需实现MCP Server即可被动态发现和调用。非MCP工具也可以通过专属连接器适配。
- **完整的调用生命周期**：记录每次工具调用的参数、结果、延迟，并可用于优化选择。

### 5.2 工具连接器基类

```python
class BaseToolConnector(ABC):
    def __init__(self, tool_id: str, config: dict, metrics: ToolMetrics):
        ...

    @abstractmethod
    async def execute(self, params: dict) -> ToolResult:
        """执行工具，返回标准结果"""
        ...

    @abstractmethod
    async def health_check(self) -> bool: ...
    
    def get_capabilities(self) -> List[str]: ...
    def get_parameters_schema(self) -> dict: ...
```

### 5.3 工具分类与示例

| 类别 | 示例工具 | 说明 |
| :--- | :--- | :--- |
| 信息获取（眼） | WebSearch (SearXNG/DuckDuckGo), LocalFileReader, DBQuery | 获取外部或本地信息 |
| 输出表达（口） | EmailSender, MessagePush, TTS | 输出结果给外部系统 |
| 操作执行（手） | CodeExecutor (沙箱), TerminalCmd, FileWriter | 执行具体操作 |
| 系统交互（脚） | BrowserAutomation (Playwright), SSHClient | 与外部系统交互 |
| 监听接收（耳） | WebhookReceiver, RSSReader | 被动接收信息 |

**工具结果标准格式**：
```python
@dataclass
class ToolResult:
    status: str        # SUCCESS / FAILED / TIMEOUT
    data: Any          # 核心数据
    metadata: dict     # 执行元数据（耗时、来源等）
    error: Optional[str]
```

### 5.4 MCP协议的集成

工具管理模块内置一个**MCP客户端/网关**，它可以：
- 发现并连接任何标准的MCP Server。
- 将MCP Server提供的工具自动注册到工具注册表中，使其能被统一路由和使用。
- 非MCP工具通过编写简单的适配连接器来统一接入。

**与认知记忆底座的协作**：
- 电报引擎在组装电报时，如果发现需要外部事实（如“最新的Python版本”），会自动调用工具模块的搜索工具，然后将结果填入`<FACTS>`。
- 大模型在回复单中也可以明确请求工具（在`uncertainties`中说明），系统会重新调用工具并重新发送电报。

### 5.5 工具调用日志与调优

与API模块类似，记录`tool_call_log`，用于分析各工具的可用性和性能，从而在多个同类工具间智能选择。

## 六、认知记忆底座（Cognitive Memory Core）

### 6.1 四库记忆与项目中心

| 记忆库 | 表名 | 关键字段 | 管理规则 |
| :--- | :--- | :--- | :--- |
| 档案馆 | `archive_memories` | id, content, metadata(JSONB), embedding vector(768), version, annotations, created_at | 允许重复，更新时新增版本，旧版本标记deprecated |
| 知识馆 | `knowledge_items` | id, key(unique), value, embedding vector, version, is_active, updated_at | 键唯一，更新版本递增，查询取最新活跃版本 |
| 常规记忆 | `general_memories` | id, content, memory_type, heat_score, last_access, access_count, tier, project_id, embedding | 按热度自动流转，记录工单、对话摘要等 |
| 保密记忆 | `secret_memories` | id, encrypted_content(bytea), key_id, access_log | 加密存储，不参与一般检索 |
| 项目中心 | `projects` | id, name, description, config(JSONB), embedding | 每个项目一个条目，关联记忆时指定project_id |

### 6.2 双权重热度管理引擎

- **热度分计算**：`heat = 0.6 * exp(-λ * hours_since_last_access) + 0.4 * (access_count / max_access_count)`
- **四级流转**：
  - 热记忆(hot)：`heat >= 70`，内存缓存+DB
  - 常温记忆(warm)：`30 <= heat < 70`，DB
  - 冷却记忆(cold)：`10 <= heat < 30`，压缩存储
  - 仓库记忆(warehouse)：`heat < 10`，仅摘要+索引
- **仓库生命周期**：超过90天标记待销毁，30天宽限期后可手动确认销毁或归档冷存储；可设置“永久保留”标签。

### 6.3 去重引擎

- **档案馆**：语义相似度>0.95视为重复，插入新版本，旧版本标记deprecated。
- **知识馆**：相同key直接更新，版本号+1。
- **常规记忆**：相似度>0.9且同memory_type则合并摘要，累加访问频次，取最大热度分。
- **电报/回复单**：TEL相似度>0.95则更新现有记录的MAIL（如果更好），增加occurrence_count。

### 6.4 双DB索引引擎（真相库与索引库分离）

- **PostgreSQL（真相库）**：存储所有记忆的完整内容、元数据、标签等。
- **pgvector（索引库）**：`memory_index`表存储软上下文摘要、标签向量、指针（truth_id, truth_table）、热度层级、项目ID等。
- **写入**：先写PostgreSQL → 生成摘要和向量 → 写入pgvector。
- **检索分层**：
  1. 指定项目？→ 加载项目索引，限定项目范围
  2. 第一层：PostgreSQL热记忆全文搜索
  3. 第二层：pgvector向量搜索（热记忆），使用混合相似度（文本向量0.7 + 标签向量0.3）
  4. 第三层：PostgreSQL常温记忆全文搜索
  5. 第四层：pgvector冷却记忆向量搜索
  6. 第五层：PostgreSQL仓库记忆
  7. 第六层：调用工具模块（如网络搜索）补充外部信息

### 6.5 电报引擎（TEL组装与MAIL校验）

**工作流程**：
1. 接收用户输入，调用本地模型进行意图分类和事实点提取。
2. 强制核实管道：提取待核实事实点 → 多源检索（本地记忆、项目中心、工具模块）→ 本地模型逐条核实 → 生成已核实事实清单。
3. 根据任务类型加载STC模板（如有），组装完整TEL。
4. 发送TEL到API管理模块，接收MAIL。
5. 本地仲裁：检查MAIL格式、status，如果NEED_MORE_INFO则自动补充检索重试，如果SUCCESS则用本地模型校验事实一致性。
6. 通过后更新记忆，并将结果返回给用户。

**电报模板进化**：成功的电报模板按任务类型存入知识馆，形成STC能力；失败的电报记录反模式。

### 6.6 STC（结构化电报能力）进化系统

- **能力树**：按“代码生成/知识问答/翻译/...”组织STC节点，每个节点包含电报模板、最佳参数、验证规则、成功率等。
- **经验提炼**：定期分析历史电报，聚类成功模板，提取反模式，自动生成改进版本。
- **自主进化**：检测频繁出现的知识缺口，自动生成探索性电报，调用工具和模型尝试解决，成功则固化为新的STC能力。

## 七、统一资源注册中心（避免幽灵数据）

### 7.1 核心表结构

- **resource_registry**：所有资源（模型、API Key、项目、记忆、STC、工具等）的唯一注册表，包含resource_id、type、status、指向实际数据的指针(data_table, data_id)等。
- **resource_relations**：记录资源间的引用、依赖、归属关系（如模型uses API Key，记忆belongs_to项目）。

### 7.2 生命周期管理

- 所有资源有统一的状态机：`active → deprecated → archived → deleted`。
- 删除/废弃前自动检查引用关系，存在依赖则阻止删除或级联处理。
- 定期完整性检查（每天），自动发现并修复孤立资源（幽灵数据）。

## 八、基础设施

### 8.1 配置管理

使用YAML配置文件，支持热加载。包含系统设置、模型定义、记忆参数、电报默认值、工具列表等。

### 8.2 插件系统

支持动态加载第三方扩展，扩展点包括：新模型连接器、新工具连接器、记忆存储后端、电报模板、专家角色、质检验收规则等。

### 8.3 事件总线

模块间松耦合通信，预定义事件如`memory.created`、`telegraph.succeeded`、`model.health_changed`等。

### 8.4 可观测性

- **指标收集**：总记忆数、各级记忆数、模型成功率、平均延迟、成本等，可对接Prometheus。
- **调用追踪**：每个电报和工具调用的完整生命周期追踪。
- **健康报告**：定期生成系统健康摘要。

### 8.5 多用户/智能体隔离

通过在核心表增加`owner_id`实现简单的多智能体/多用户数据隔离。
